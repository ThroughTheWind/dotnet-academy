# 01 Development Environment And CLI

## Why This Matters

Everything else in this course assumes that the learner can trust their development environment and can drive a basic workflow from the terminal.

That matters for three reasons:

1. The CLI works across editors and operating systems, so it gives the learner one reliable workflow regardless of tool choice.
2. Modern .NET development, CI pipelines, and troubleshooting all depend on commands like `dotnet restore`, `dotnet build`, `dotnet run`, and later `dotnet test`.
3. When something breaks, understanding the SDK, generated files, and command output is usually faster than guessing inside an IDE.

## Concepts

### 1. What You Need Installed

For this course, the baseline is:

- .NET 10 SDK
- a terminal you are comfortable using
- an editor or IDE such as VS Code, Visual Studio, or Rider

The important distinction is this:

- The runtime lets you run existing .NET applications.
- The SDK lets you create, build, test, and publish .NET applications.

If a learner installs only the runtime, they will be able to launch some apps but will not be able to create or build the course projects.

### 2. Verify The Installation

The first commands a learner should know are:

```powershell
dotnet --version
dotnet --list-sdks
dotnet --info
```

What to look for:

- `dotnet --version` should report a `10.x` SDK.
- `dotnet --list-sdks` should show at least one installed SDK path.
- `dotnet --info` should show the active SDK and basic environment details.

If `dotnet` is not recognized, the issue is usually one of these:

- the SDK was not installed
- the terminal needs to be restarted after installation
- the `PATH` was not updated correctly

### 3. The Core CLI Workflow

The command-line workflow used throughout the course starts small:

```powershell
dotnet new console -n HelloDotnetAcademy
cd HelloDotnetAcademy
dotnet restore
dotnet build
dotnet run
```

What each command does:

- `dotnet new console -n HelloDotnetAcademy` creates a new console application from a template.
- `dotnet restore` downloads any required packages and prepares dependencies.
- `dotnet build` compiles the project.
- `dotnet run` builds if needed and then runs the application.

Other useful discovery commands:

```powershell
dotnet new list
dotnet --help
dotnet new --help
```

These help learners discover templates and reduce guesswork.

### 4. The Files The CLI Generates

After creating a new console app, the learner should recognize these files and folders:

- `Program.cs`: the entry point of the application.
- `<project-name>.csproj`: the project file that defines the SDK and project configuration.
- `bin/`: compiled build output.
- `obj/`: intermediate build files generated by the build process.

At this stage, the learner does not need to edit the project file heavily, but they should know that it exists and that it controls how the project is built.

### 5. CLI-First Habits That Will Matter Later

These habits make the rest of the course easier:

- run commands from the correct directory and pay attention to the current path
- read command output instead of skipping past it
- use `--help` instead of guessing command syntax
- treat generated output folders like `bin/` and `obj/` as disposable build artifacts, not source files

### 6. Editor Choice Without Tool Lock-In

The learner can use VS Code, Visual Studio, or Rider, but the course will keep the core workflow editor-agnostic whenever possible.

That means:

- the terminal workflow is the source of truth
- IDE features are helpful accelerators, not hidden dependencies
- commands shown in the lesson should still work in a clean terminal session

## Common Mistakes

- Installing the runtime instead of the SDK.
- Running commands from the wrong directory and assuming the CLI is broken.
- Editing files inside `bin/` or `obj/` instead of source files.
- Assuming the IDE hid a problem when the terminal output already explained it.
- Ignoring SDK version information when multiple SDKs are installed.
